# 产品设计与策略验证

TagLab 用一个具体的内容分类任务，探索模型能力怎样进入可检查、可复核的工作流程。项目同时覆盖内容理解、评测与数据质量，以及规则设计、错误分析和策略验证。本文把这些能力对应到实际决策、代码与验证记录。

## 从什么问题开始

设想内容产品需要按主题和节目形式组织播客。让模型输出标签很容易，但产品负责人还需要回答：分类依据是什么、遇到资料不足时怎么办、提示策略变更后怎样判断是否值得采用，以及人工参考本身出错后如何追溯。

当前原型面向标注与内容运营、模型评测、产品策略三类工作角色。这是围绕任务提出的使用场景，尚未通过外部用户访谈验证需求规模。已完成的真实操作来自项目使用者，不能替代生产环境用户研究。

输入限定为标题和清洗后的简介，输出包含主题、节目形式、逐字引用与复核状态。简介无法支持的判断允许保留未知。下游可将这些标签用于整理、筛选或检索，但本项目尚未验证对发现效率、点击或留存的影响。

## 两条工作主线如何衔接

| 能力方向 | 产品工作 | 实现与证据 |
| --- | --- | --- |
| 内容理解与标签体系 | 把“主要讨论什么”和“怎样组织对话”分开；定义标签包含与排除条件，避免见到关键词就加标签。 | [标签规范](../workbench/taxonomy.json)：6 个主题、最多选 3 项；4 种形式，包含无法判断。 |
| 数据清洗与质量检查 | 保留原始输入、删除内容、截断和短文本提示；检查清洗是否损失判断所需信息。 | [数据处理与评分](../workbench/core.py)；清洗记录可回看。清洗规则本身仍需要误删检查。 |
| 模型评测与实验设计 | 比较同一模型在基础提示与定义、反例提示下的输出，固定输入、参数和共同输出协议。 | [模型适配与协议](../workbench/model_adapter.py)、[实验记录](PILOT-20261108.md)。 |
| 规则与策略落地 | 将规则分配到提示词、程序校验和人工裁决；针对不同风险选择处理方式。 | [Argilla 数据交换](../taglab_argilla.py)、[提案暂存与裁决](../workbench/argilla_bridge.py)。 |
| 错误分析与版本判断 | 区分模型错误、信息缺失与参考争议；记录为什么改规则或修订参考。 | [参考修订分析](../workbench/reference_audit.py)、[验证记录](VALIDATION.md)。 |

因此，数据质量决定比较是否可信，错误分析又会暴露标签定义或策略中的问题。项目将两者放在同一条流程中，避免只看总分而忽略分数的来源。

## 四个关键取舍

**允许未知，而不是强制补齐。** 简介没有写嘉宾，不等于节目一定为独白。形式不确定时使用 unknown；主题仍可独立判断。这降低了强行猜测的风险，但未知比例过高也可能减少可用标签，需要另行观察。

**程序检查引用存在，人工检查引用是否充分。** 连续字符串匹配能阻止改写或拼接后冒充引文，不能证明语义支持或外部事实真实性。两类检查分别记录，不能将机械通过率宣传为分类准确率。

**盲标与机器复核分开。** 独立标注不显示机器建议；看过机器候选后的反馈保留其来源，不从盲标入口直接成为独立评分参考。这样能减轻把模型答案循环写回参考的风险，但当前单人标注仍不等于多人共识。

**旧实验保留，参考修改另存分析。** 参考错误需要修订，同时保留原快照。保持模型预测不变时的分数变化，解释为评分依据变化；输入或标签规范变化时，拒绝直接复用旧预测。

## 用失败案例检查策略

以下问题来自已保存的真实运行与复核。它们用于定位原因，不代表对全部数据的发生率估计。

| 观察到的问题 | 原因判断 | 处理与验证 |
| --- | --- | --- |
| 用省略号拼接多段原文作为引用 | 未满足共同输出协议，不能当作连续引文。 | 拒绝该输出，保留原字段、用量和错误；不自动修补后计成功。 |
| 输出独白却没有形式依据 | 实际字段与依据要求不一致；解释中承认不确定也不能代替合规字段。 | 按实际字段校验，保留失败供复盘。 |
| 引文确实存在，但没有说明讲话人数 | 字符串有效，语义支持仍不足。 | 进入独立机器复核任务；保留争议意见，不作为独立评分参考。 |
| 人工参考的生活方式标签缺少充分依据 | 差异也可能来自参考，不能默认两个策略都错。 | 按用户明确确认修订一条参考，另存复算结果，保持原实验不变。 |

人工粘贴引文末尾多余空白属于另一类问题：只有去除首尾空白后能精确匹配原文才允许规范化，并保留前后值；不据此放宽模型引用规则。

## 怎样验证一次策略变更

本轮离线配对实验检查的问题是：加入定义与反例后，输出是否更符合标签规范，错误与复核需求如何变化。这里的 A/B 是同一输入上的提示策略比较，没有线上用户流量分配，也没有训练模型权重。

1. 查看输出前固定 pilot 的 10 条输入，两组使用相同模型、参数与输出协议；A 为基础提示，B 增加定义和反例。
2. 保存每次请求的输入版本、提示词、结果、用量与错误，不将失败静默替换成成功输出。
3. 一起查看协议通过、标签指标、形式判断、分歧、复核标记与调用成本信息，避免只凭一个分数决定。
4. 对分歧回到原文定位原因，再判断需要改提示、改规范、补资料还是修订参考。
5. 若继续迭代，在开发样本上修订；另行准备足够独立的参考并冻结验收方案，再使用留出集作后续检验。

已完成的是小样本实验、错误复核和参考修订追溯。尚未形成可信的优胜策略结论，也没有完成留出集锁定验收。后续扩样时应补足主题覆盖、独立标注与重复运行，并预先确定验收阈值。

## 指标怎样服务产品判断

| 指标或记录 | 回答的问题 | 当前状态 |
| --- | --- | --- |
| 格式与连续引用通过率 | 输出能否进入后续处理？ | 本轮 18/20；只代表机械校验，不代表内容正确。 |
| 主题 micro F1、形式匹配、完全匹配 | 相对当时的人工参考，标签差异在哪里？ | 原实验仅 4 条有效参考，修订前后另存，不能外推整体能力。 |
| 分歧与复核标记 | 哪些记录优先查看？ | 8 条两组均合规记录中有 5 条标签或形式不同；标记复核不等于已识别所有错误。 |
| Token、延迟与失败原因 | 更多规则带来哪些调用开销与故障？ | 请求级记录已保留；Token 是接口用量，不能直接当作现金账单。 |
| 自动采用覆盖率、采用部分错误率、人工复核耗时 | 能否节省工作，同时将错误控制在可接受范围？ | 待设定采用规则与开展使用测试，当前没有业务收益结论。 |
| 独立标注者一致性 | 标签规范是否容易理解和稳定执行？ | 待增加独立标注者，当前不能用助手复核代替双人一致性。 |

## 当前交付与使用边界

截至 2026-11-08，已整理 80 条来自两档节目的真实 RSS 元数据，本地保留 7 条人工参考与 8 次实验记录；一次配对运行包含 20 次真实模型调用。40 项应用测试覆盖数据交换、版本冲突、引用、裁决和参考复算等路径；这些是流程与工程验证，不等于模型评测样本。

当前项目能展示问题定义、标签与规则设计、API 原型、模型实验、错误分析和版本审计。尚未验证外部用户需求、多人协作效率或线上效果；没有音频理解、微调或 RAG 实验。原始语料、私人标注、完整模型输出和密钥不公开，公开代码和合成测试可按[使用说明](../README.md)运行。
