# TagLab 的技术原理与本轮实现

这个项目研究的是：当模型给一段内容打标签时，我们如何界定什么算正确、发现错误、收集可信的人类判断，并验证一次修改是否有用。Fork 的用途是把这些判断放进可追溯的协作流程，而不是把开源项目换个名字。

## 一、系统怎样分工

现在有两层应用：

- **TagLab 本地工作台**：采集公开 RSS 标题与简介，清洗文字，保留原文，管理人工参考，调用百炼模型，运行 A/B 实验，检查输出并计算指标。现有数据和密钥继续留在这里。
- **Argilla Fork**：提供成熟的标注任务结构、模型建议和用户回答机制。本轮扩展负责把两边的数据对齐，并把 Argilla 回答转换成“待裁决提案”。当前完成的是 SDK 和协议对接，完整服务还未启动。

Argilla 的服务架构包括网页前端、Python API、关系数据库、Elasticsearch、Redis 和后台 Worker。数据库保存记录、用户回答等持久状态；Elasticsearch用于检索与过滤；Redis和Worker处理后台任务。大模型不在这些组件里自动运行：本项目由TagLab调用百炼，再把结果作为候选送给Argilla。

Fork 是保留上游来源关系的代码副本。SDK连接是两个系统在运行时交换数据。创建Fork不等于已经部署，更不等于系统已经跑过线上同步；这三种状态需要分别验证。

## 二、一个样本不是一段随时可以覆盖的文字

同一条播客记录包含稳定ID、标题、清洗简介、数据分组、输入哈希和参考版本号。输入哈希用排序后的JSON和SHA-256生成。标题、简介任意一个字变化，哈希就变化。

这解决的是“模型到底看过哪份文字”。例如先把广告删除，再给模型分类，随后人工却看原始广告较多的简介，双方判断可能根本不是同一个任务。因此导出包保留精确输入，回收时检查输入和参考版本。它能发现意外变更，不能替代登录授权，也不是防伪签名。

本轮盲标字段不包含节目名、RSS分类和既有标签，避免人或模型凭频道定位直接猜答案。但当前两档节目本身以商业科技为主，这种采样偏差仍然存在，不能靠隐藏节目名消除。

## 三、为什么要把建议、回答和裁决分开

Argilla的三类数据有不同含义：

1. Record：待处理的输入材料。
2. Suggestion：模型建议，不代表有人认可。
3. Response：某个用户提交的回答，保留用户身份和提交状态。

本轮扩展再增加了Proposal暂存层。一个Response只有在已提交、标签合法、原文引用有效、输入未变、版本未冲突时，才能进入Proposal；只有明确执行裁决并留下理由，才可以更新TagLab参考。

两个审核者回答不同，不应“取最后一次”覆盖。我们保留每人的回答，之后才讨论是否需要仲裁。即使人填了标签，也只是有来源的人类判断，不能宣称绝对真理。

还区分两种工作模式：盲标模式不显示机器结果，可以形成相对独立的参考；复核模式会显示机器结果，适合定位错误，但有锚定偏差，不能悄悄当成独立金标准。当前裁决入口禁止把复核模式提案直接升级为独立参考。

## 四、模型实际在做什么

输入是标题与简介，输出是最多3个主题（多标签分类）、1个节目形式（单标签分类）、每个判断的原文引用及待复核状态。模型通过提示词条件化生成这些字段；本项目没有训练或修改模型参数。

A组只获得标签ID和名称，B组额外获得定义、边界和反例。两组共用JSON格式与连续原文引用协议，使用相同模型、输入和生成参数。比较的是具体策略差异，不是笼统地比较“哪家AI更好”。

temperature设为0.2只减少生成波动，不能保证每次完全一致。单轮结果可能来自随机性。要证明改进，需更多独立参考、配对样本和重复实验；同时修改多项条件，也不能把提升全归因于某一句提示词。

当前没有做RAG、向量检索、微调或RLHF。后续可把经过裁决的资料用于训练，但“有了反馈数据”不等于“已经训练模型”。

## 五、校验为什么要分层

第一层：接口是否成功，有无鉴权、超时、限额等问题。
第二层：是否是合法JSON。
第三层：标签ID、数量、类型是否符合规范。
第四层：引用是否为本次输入中连续出现的原文，不能用省略号拼接。
第五层：这段真实原文是否足以支持该标签。
第六层：即使输出合法，是否仍需要人工复核，是否可以自动采用。

前四层主要由程序检查，后两层需要更谨慎的人类判断和决策规则。

本项目已经出现实际反例：《郎的诱惑》的模型B引用了“基于报道拆解分析”，原文确实存在，所以通过字符串校验；但据此判断“独白”缺少证据，因为简介并没有说明只有一人讲话。你的参考是“无法判断”。这属于“真实引用支持不了结论”，与凭空捏造引用是不同错误。

另一个反例是将多段原文用省略号串成证据：这些词可能各自出现过，但不是连续原文，引用契约检查会拒绝。我们不会自动拼接修复后算作模型成功。

## 六、指标怎样计算，为什么不能只说准确率

主题是多选，必须分清：选对TP、多选FP、漏选FN。把样本汇总后：

- Precision = TP / (TP + FP)，衡量选出的标签有多少正确。
- Recall = TP / (TP + FN)，衡量应选标签找回多少。
- Micro F1 = 2TP / (2TP + FP + FN)，平衡多选与漏选。

形式准确率单独计算。完全匹配要求整组主题和节目形式都与参考一致。每类标签的样本支持数也必须保留，否则只有商业类正确，不能说明文化类也好。

当前工作台的端到端指标把输出校验失败按未命中计。这有助于评价系统能否完成任务，但需要同时显示格式通过率和错误类别：格式失败与语义分类错误不是同一问题。

另一个边界是：当前评分也会比较needs_review=true的合法输出，因此它不代表自动采用后的正确率。真正用于业务，还要统计自动采用覆盖率、人工介入率、自动采用子集的错误率。后续应明确阈值与人工成本，不能用高F1掩盖全部转人工。

现在只有少量独立参考，单条匹配100%只能描述单条，不能当成模型总体能力。现有5条人工参考不被覆盖；2条留出参考不进入开发调试。

## 七、本轮为什么是真正的工程改动

实际Fork：https://github.com/MariaMaizi/taglab-argilla

上游基点：5338519accb13ae422f8bf9c0642651c249c49af。

新增examples/taglab应用扩展、可公开的workbench代码、数据交换和测试。还修复了SDK干净安装时漏声明requests依赖，以及传入自定义transport会重复传参的问题。自定义transport使SDK可以在不连接外部服务时进行可重复的协议测试。

测试使用真正的Fork SDK对象，仅把HTTP认证响应模拟。模拟认证不等于真服务器部署；它验证对象、序列化、回答状态、错误路径和本地数据事务。当前28项测试通过，仍有上游Pydantic弃用警告，文档如实保留。

人工提案接受、参考更新和审计记录在同一个SQLite事务中提交，配合版本检查，避免并发更新覆盖他人判断。待裁决提案按稳定ID去重；重复导入不会重复生成参考。

## 八、下一步的真实阻塞与验收

电脑缺少Docker与WSL Linux环境，所以Argilla网页服务尚未启动。本轮准备了只绑定127.0.0.1:6900的Docker Compose，使用官方v2.8.0镜像；没有修改Argilla网页和服务端源码，也没有声称在运行自建服务镜像。

安装Docker Desktop并使Linux引擎可用后，才可继续验收：启动容器→登录→用SDK创建盲标任务→在Argilla网页提交回答→拉回提案→检查原文、作者、版本→显式裁决→新建实验。

在这之前，不需要再次提供百炼密钥，也不需要重做已经完成的标注。原有TagLab服务没有为本轮SDK工作而重启。

参考：Argilla官方仓库、Records/Responses/Suggestions文档与Docker部署文档。英文架构说明和实现边界也随Fork代码保存，方便代码审阅。
